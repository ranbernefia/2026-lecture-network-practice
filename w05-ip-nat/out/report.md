# 5주차 Task 2 · 내 주소 조사 보고서

측정: 2026-10-15, 같은 컴퓨터(Windows 10)에서 두 네트워크
- `home-ethernet`: 집 유선 (공유기)
- `iphone-tethering`: 아이폰 USB 테더링 (휴대폰 데이터)

원본 출력은 `out/addresses.json`, DHCP 캡처는 `out/dhcp.pcapng`.

## Part A · 내 주소 (집 유선)

**A1. 내 주소와 마스크** — `ipconfig /all`의 이더넷 항목에서 직접 읽음

| 항목 | 값 |
|---|---|
| IPv4 주소 | 192.168.35.70 |
| 서브넷 마스크 | 255.255.255.0 (= /24) |
| 기본 게이트웨이 | 192.168.35.1 |
| DHCP 서버 | 192.168.35.1 |

**A2. 주소 범위 (손 계산 → Task 1로 확인)**

마스크 255.255.255.0은 앞 24비트가 1이라 /24다. 주소의 앞 세 칸은 그대로 두고 마지막 칸을 0으로
만들면 네트워크 주소 192.168.35.0이 된다(70 AND 0 = 0). 마지막 칸 8비트가 집 번호라 주소는 256개다.

- 네트워크 주소 192.168.35.0, 첫 사용 가능 192.168.35.1, 마지막 사용 가능 192.168.35.254, 브로드캐스트 192.168.35.255
- Task 1의 `network_range("192.168.35.0/24")` 결과 `('192.168.35.1', '192.168.35.254', '192.168.35.255')`로 손 계산과 같다.

**A3. 게이트웨이가 범위 안에 있나?**

192.168.35.1로 범위(1~254) 안에 있다. 같은 동네 안에 있어야 컴퓨터가 라우터 없이 직접(이더넷으로)
보낼 수 있기 때문이다. 게이트웨이가 범위 밖이면 그 게이트웨이까지 가는 데 또 게이트웨이가 필요해져서
아무 데도 못 나간다.

**A4. 바깥에서 본 주소** — `api.ipify.org`가 본 주소: **211.187.75.22**

**A5. 사설/공인, NAT는 몇 겹?**

- 192.168.35.70은 사설 주소(RFC 1918의 192.168.0.0/16)이고, 211.187.75.22는 공인 주소다. 둘이 다르니 NAT가 적어도 하나 있다.
- **1겹이라는 증거**: 공유기에게 UPnP로 "네 바깥쪽 주소가 뭐야?"(GetExternalIPAddress)라고 물었더니
  `211.187.75.22`라고 답했다. 공유기가 가진 바깥 주소가 인터넷에서 보인 주소와 같으니, 공유기 뒤에
  다른 NAT가 없다. 즉 **NAT 1겹(집 공유기)**이다.
- **1겹과 2겹을 구별하는 법**: 공유기의 바깥쪽 주소를 확인한다. 그 주소가 인터넷에서 본 주소와 같으면 1겹,
  `10.x`나 `100.64.x` 같은 사설 주소라면 통신사 쪽에 NAT가 하나 더 있는 2겹이다.
  (`tracert`는 첫 구간 192.168.35.1 이후로 응답이 막혀 있어서 이 방법으로는 확인할 수 없었다.)

## Part B · 두 네트워크 비교

| | 집 유선 | 아이폰 테더링 |
|---|---|---|
| 내 주소 (사설) | 192.168.35.70 | 172.20.10.4 |
| 마스크 | 255.255.255.0 (/24, 256개) | 255.255.255.240 (/28, 16개) |
| 주소 범위 | .1 ~ .254, 브로드캐스트 .255 | 172.20.10.1 ~ .14, 브로드캐스트 .15 |
| 게이트웨이 | 192.168.35.1 (공유기) | 172.20.10.1 (아이폰) |
| 바깥에서 본 주소 | 211.187.75.22 | 211.235.73.23 → 1분 뒤 211.235.72.144 |
| IPv6 | 링크 로컬(fe80::)만 있음 | 공인 IPv6 주소(2001:2d8:...)를 받음 |

테더링 범위 손 계산: 마스크 240 = 11110000이라 마지막 칸의 앞 4비트만 동네다. 4 = 00000100에 마스크를
씌우면 0이므로 네트워크는 172.20.10.0/28, 주소는 2^4 = 16개다. Task 1 `network_range("172.20.10.0/28")`도
`('172.20.10.1', '172.20.10.14', '172.20.10.15')`로 같다. 172.20.x는 RFC 1918의 172.16.0.0/12 안이라 사설이다.

**B3. 공인 주소와 사설 주소가 바뀌었나?**

- **공인 주소가 바뀌었다** (211.187.75.22 → 211.235.x.x). 인터넷에 나가는 출구가 집 공유기에서 휴대폰
  통신사로 바뀌었기 때문이다. 바깥에서는 내 컴퓨터가 아니라 그 출구의 주소만 보인다.
- **사설 주소도 바뀌었다** (192.168.35.70 → 172.20.10.4). 사설 주소는 그 동네의 DHCP 서버가 나눠 주는데,
  유선에서는 집 공유기가, 테더링에서는 아이폰이 DHCP 서버라서 각자 자기 동네 번호를 줬다.
  아이폰은 기기 몇 대만 붙으면 되니 /28(16개)로 작게 잡았다.

**테더링의 NAT는 몇 겹?** 1겹째는 아이폰이다(게이트웨이 172.20.10.1이 아이폰이고, 172.20.10.4를 아이폰
자신의 주소로 바꿔 내보낸다). 그런데 바깥에서 본 주소가 다시 연결하지도 않았는데 1분 만에
211.235.73.23에서 211.235.72.144로 바뀌었다. 아이폰이 공인 주소를 직접 받았다면 연결 중에 바뀔 이유가
없으므로, 통신사가 여러 공인 주소를 돌려 쓰는 NAT(통신사 NAT)를 한 번 더 거치는 **2겹**으로 보인다.
아이폰은 자기 데이터 주소를 보여주지 않아서 직접 확인하지는 못했다.

## Part C · DHCP 캡처 (`out/dhcp.pcapng`)

집 유선에서 `ipconfig /release` 후 `ipconfig /renew`로 주소를 다시 받으며 캡처했다.

| 번호 | 메시지 | 보낸 주소 → 받는 주소 | 받는 MAC |
|---|---|---|---|
| 1 | Release (반납) | 192.168.35.70 → 192.168.35.1 | 공유기 |
| 2 | **Discover** | **0.0.0.0 → 255.255.255.255** | ff:ff:ff:ff:ff:ff (전체) |
| 3 | Offer | 192.168.35.1 → 192.168.35.70 | 내 컴퓨터 |
| 4 | Request | 0.0.0.0 → 255.255.255.255 | ff:ff:ff:ff:ff:ff (전체) |
| 5 | Ack | 192.168.35.1 → 192.168.35.70 | 내 컴퓨터 |

**C1.** Discover(2), Offer(3), Request(4), Ack(5) 네 개가 모두 있다.

**C2. Discover의 주소** — 보낸 주소 `0.0.0.0`, 받는 주소 `255.255.255.255`.
이상한 쪽은 보낸 주소 0.0.0.0이다. 컴퓨터는 지금 주소를 받으려는 중이라 아직 자기 주소가 없으니
"주소 없음"을 뜻하는 0.0.0.0을 쓸 수밖에 없다. 또 DHCP 서버가 어디 있는지도 모르니 받는 주소도
특정할 수 없어서, 동네 전체에 보내는 255.255.255.255로 외친다.

**C3. 빌려주는 기간(lease time)** — Offer와 Ack 모두 **3600초 = 1시간**.

**C4. Discover는 전체 방송인데 Ack는 왜 아닌가?**

Discover를 받은 공유기가 그 안에서 내 컴퓨터의 MAC 주소를 알게 됐고, 줄 주소(192.168.35.70)도 정했다.
그래서 Offer와 Ack는 전체에 외칠 필요 없이 내 MAC 주소로 콕 집어 보낼 수 있다.
(Request는 여전히 전체 방송이다. 다른 DHCP 서버들에게도 "나는 이 서버의 제안을 골랐다"고 알리기 위해서다.)
